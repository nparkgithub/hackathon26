ZERO-CONFIG SERVICE DISCOVERY

mdns

Android ⇄ Windows device monitor over mDNS

An Android app advertises _devmon._tcp and serves TCP. A Windows Python client discovers it and streams back its IP, network interface, and CPU usage.

Kotlin · NsdManager · Python · zeroconf · psutil
Opening frame. Two halves, one protocol. The problem this solves: two devices on the same WiFi, neither knowing the other's address. No config file, no QR code, no typing IP addresses. That's what mDNS buys you. Say up front where this stands: both halves are built and verified working. The Python side was tested end to end, the APK compiles and runs, and the whole thing was exercised on a real emulator. There is one significant limitation about emulators that we'll get to on slide 6 — don't bury it, but don't lead with it either.

Architecture

Build this up in four clicks — don't dump it all at once. Click 1 — the two components. Note the asymmetry: the phone is the SERVER here, which surprises people. The phone advertises and listens; the PC connects and pushes. We chose that way round because the PC has the interesting telemetry. Click 2 — mDNS discovery. Dashed and animated on purpose: this is UDP multicast, fire-and-forget, no handshake. Both arrows because discovery is bidirectional — the browser queries, the advertiser announces. Click 3 — the TCP stream. Solid line, one direction: PC to phone. Newline- delimited JSON, one object per sample, roughly every 2 seconds. Click 4 — the constraint that governs everything else. mDNS is link-local, TTL 1. Same subnet or it does not work. This single line explains the emulator problem, the 2.4-vs-5GHz gotcha, and the AP-isolation gotcha all at once. If asked why not just type an IP: phone IPs change on every DHCP lease.

How the client learns the address

discover_and_report.py — from multicast query to first JSON frame. Nothing is configured; every value below is learned at runtime.

1 · What mDNS actually returns

# browse: "who serves _devmon._tcp?"  → UDP 224.0.0.251:5353
ServiceBrowser(zc, "_devmon._tcp.local.", listener)

# the phone answers with three record types:
PTR  _devmon._tcp.local  → devmon-pixel._devmon._tcp.local
SRV  devmon-pixel…       → host NPARK.local port 41979
A    devmon-pixel.local  → 192.168.1.42
TXT  role=android-advertiser model=Pixel sdk=36

2 · Extract host + port

def add_service(self, zc, type_, name):
    info = zc.get_service_info(type_, name, timeout=3000)
    ip, port = self._describe(info)   # ← A + SRV

def _describe(info):
    addrs = info.parsed_addresses(IPVersion.V4Only) \
            or info.parsed_addresses()
    return addrs[0], info.port

Prefer IPv4

Phones often answer with IPv6 link-local and IPv4. Taking v4 first avoids scope-id handling on Windows; the fallback keeps v6-only peers working.

First of two mechanics slides. Three clicks. Click 1 — the records. This is the part most explanations hand-wave. Browsing is not one lookup; it's three record types doing different jobs. PTR answers "who exists" and gives you only a NAME. SRV maps that name to a hostname and a PORT. A maps the hostname to an IP. TXT carries free-form metadata — we use role, model and sdk. The key point: you need PTR plus SRV plus A before you can open a socket. A name alone is useless. zeroconf's get_service_info does all three lookups and blocks up to three seconds. Click 2 — extraction. Short function, two real decisions in it. Click 3 — the IPv4 preference. Worth a sentence: a phone will typically announce both an IPv6 link-local address and an IPv4 one. IPv6 link-local needs a scope id to be usable, which is a portability headache on Windows, so we take v4 when it exists and fall back otherwise. If there is no address at all we bail rather than construct a Reporter pointed at nothing. Next slide: what we do with the address once we have it.

Connect, frame, push

Discovery handed us ip and port. One thread per peer takes it from there.

3 · Dial it, keep it alive

r = Reporter(name, ip, port, interval, verbose)
r.start()          # one daemon thread per peer

def run(self):                       # reconnect loop
  while not self._stop.is_set():
    try:
      with socket.create_connection(
              (self.host, self.port), timeout=5) as s:
        self._pump(s)
    except OSError as e:
      print(f"{e} - retrying in 3s")
    self._stop.wait(3)

4 · Frame and push

def _pump(self, sock):
  while not self._stop.is_set():
    payload = telemetry(self.host, self.port)
    sock.sendall((json.dumps(payload) + "\n").encode())
    self._stop.wait(self.interval)     # 2 s

The peer address feeds back in

telemetry(self.host, …) takes the discovered IP and asks the OS which local interface routes to it — so the reported ip/interface is the one facing that phone.

Why newline-delimited JSON

Not length-prefixed, not one object per connection. The Kotlin reader is BufferedReader.readLine() — the simplest correct parser available.

Two details that matter

sendall not send — send can write partially. And the 5 s connect timeout stops a discovered-but- unreachable phone hanging the thread.

Second mechanics slide. Five clicks — two code blocks on the left, three cards on the right. Click 1 — the connect. Two things worth calling out. It's a thread per peer, so several phones stream concurrently and one dropping doesn't disturb the others. And create_connection sits inside a while loop with a three-second backoff, so WiFi dropping out is a pause rather than a crash. That reconnect path was exercised in testing when a service record went stale and the port changed underneath us. Click 2 — the send loop. Build the payload, serialise, append a newline, sendall, sleep two seconds. That's the whole protocol. Click 3 — the subtle design point, and the one I'd want an interviewer to ask about. We pass the phone's address into telemetry(), because "what is my IP" has no single answer on a machine with eight interfaces. The only correct answer is "the address that routes to you" — and only the peer's address can determine that. Click 4 — format choice. Newline-delimited JSON keeps the Android parser to a single readLine() call. Length-prefixing would be marginally more efficient and considerably more code on both sides. Click 5 — the two easy-to-miss details. sendall loops until the whole buffer is written; send can return having written part of it, which silently corrupts a frame. And without the connect timeout, a phone that advertised but isn't reachable — asleep, firewalled — would block that thread indefinitely. Likely question: what if the port changes? update_service fires, we tear the Reporter down and re-add it.

How often does the phone announce?

Not a config value in this codebase — it's dictated by RFC 6762 §8.3, and the platform's mDNS responder enforces it, not our app.

1 · The announce burst

# §8.3: at least 2 unsolicited responses, spaced 1s apart
t=0.0s   announce  # registerService() returns
t=1.0s   announce  # required minimum: 2 total
t=3.0s   announce  # optional, up to 8 total
t=7.0s   announce  # each gap ≥ 2× the last
# ...then silence. Only answers queries after this.

No heartbeat

§8.3 is explicit: "MUST NOT send regular periodic announcements." The burst above is the whole lifetime — no re-advertise loop is hiding in AdvertiserService.

TTL, not a retry timer

A (Address, IPv4) / AAAA (Address, IPv6): 120 s. PTR (Pointer) / SRV (Service) / TXT (Text): 75 min. Goodbye packets set TTL=0 so listeners purge the entry almost immediately.

2 · How to actually see it

Capture on the Windows side

No root needed — multicast is visible to any host on the subnet:

tshark -i Wi-Fi -f "udp port 5353" \
  -Y dns -T fields -e frame.time_relative \
  -e ip.src -e dns.qry.name

Or capture on the emulator

adb shell tcpdump -i any -n 'udp port 5353' -w /sdcard/mdns.pcap, then adb pull and open in Wireshark, filter mdns.

Cheapest option: no capture at all

Bump zeroconf's logger to DEBUG in discover_and_report.py — every received PTR/SRV/A retransmission logs with a timestamp, on tooling already in this repo.

This slide exists because of a direct question: how often does the phone re-send its advertisement, and how would we check that ourselves instead of taking my word for it. Click 1 — the timeline. RFC 6762 section 8.3 requires at least two unsolicited responses one second apart, and permits up to eight total with each gap at least doubling the last — 1, 2, 4, 8 seconds and so on. That's a bounded burst at registration time, not a recurring schedule. Click 2 — the part people usually get wrong. The RFC says outright: must not send regular periodic announcements. So there is no timer in AdvertiserService because there shouldn't be one — the phone announces once (as a short burst) and then only responds when queried. This directly explains the "unregistered" log line from earlier testing — that was a discrete event, not a missed heartbeat. Click 3 — TTL is the mechanism that actually governs freshness, and it isn't one-size-fits-all. Address records — A for IPv4, AAAA for IPv6 — expire in 120 seconds because a phone's IP churns with every DHCP lease renewal. The identity-level records — PTR, the pointer that says the service exists; SRV, the service record that maps the instance to a hostname and port; and TXT, the free-form text metadata — all get 75 minutes, because that information barely ever changes. A clean shutdown sends the same records again with TTL zero as a "goodbye," so caches drop them in about a second instead of waiting out the full TTL. Click 4 through 6 — three ways to verify this independently rather than trust the RFC text alone. Capturing on the Windows side is the easiest: it's the same subnet, so multicast is visible to any host, no root required. The emulator route needs tcpdump over adb. The cheapest option needs no packet capture at all — zeroconf already logs every record it receives, so a DEBUG log level surfaces the same retransmission pattern through code already in this repo. If asked "so is 53 seconds normal for a re-register" — no, that number doesn't come from this RFC section at all; it's worth capturing traffic to find the actual cause rather than assuming it's expected mDNS behavior.

After the TTL split — who resends, and when?

Neither on a schedule. TTL expiring is a receiver-side event — the phone has no clock counting down to a resend.

1 · Responder (phone) — two triggers only

Asked a question

A query for _devmon._tcp or the instance/hostname arrives → the phone answers immediately, any time, regardless of how long it's been advertising. This is the steady state — it doesn't proactively broadcast, it just answers.

Something actually changed

IP changes (new DHCP lease, network switch) or the service re-registers on a new port → the platform's mDNS responder announces the changed records with the cache-flush bit set. RFC 6762 §10.1 — react to a real change, not a timer.

Still no heartbeat

§8.3's "no regular periodic announcements" rule applies here too. This logic lives in the OS mDNS stack under NsdManager, not in AdvertiserService.

2 · Receiver (Windows/zeroconf) — drives the cadence

Proactive re-query near TTL%

RFC 6762 §5.2: re-query at 80 / 85 / 90 / 95% of TTL. For a 120 s A record that's ~96 s, 102 s, 108 s, 114 s — each usually answered instantly by trigger 1, refreshing the cache before it ever expires.

Silent expiry if unanswered

If the phone is genuinely gone, none of those re-queries get a reply, and the record quietly ages out at 100% of TTL — no explicit goodbye needed for that path.

What tshark actually shows

Resend traffic isn't "phone rebroadcasting on a schedule" — it's Windows re-asking near the TTL boundary, phone answering because it was asked. The phone is passive; the client drives the refresh cadence.

This slide exists to correct a natural assumption: that TTL expiring makes the phone resend. It doesn't — TTL is purely a receiver-side bookkeeping value. Click 1 and 2 — the only two things that make the responder emit anything after the initial announce burst. Either it gets asked (the normal steady state — any query gets an immediate answer, at any time), or something concrete changed (IP, port) and the OS's mDNS responder announces just the changed records with cache-flush set. Click 3 reinforces that this is still governed by "no periodic announcements" — it's OS-level reactive logic, not a loop in our Kotlin code. Click 4 and 5 — the receiver side is where TTL actually drives behavior. zeroconf (and any RFC-compliant mDNS client) re-queries a record it still cares about at 80, 85, 90, and 95 percent of its TTL, specifically so the cache refreshes before expiring. If the phone answers — which it will, per click 1 — the receiver never even notices a gap. If the phone is truly gone, those re-queries go unanswered and the record just ages out silently at 100 percent; no goodbye packet is required for that path, only for a clean, intentional shutdown. Click 6 — ties it back to what you'd actually see in a capture. Don't mistake periodic re-query traffic from the Windows side for the phone "checking in." The phone only ever answers; Windows is the one polling on a TTL-driven schedule.

Route-aware, not naïve

ip and interface are resolved with a connectionless UDP socket — the address the OS would actually use to reach the phone, not the first NIC in the list.

Six clicks, one per step. The two cards on the right land with steps 5 and 6. Step 1 is the subtle one and worth pausing on. Bind before register. If you register first you have no port to put in the SRV record, and a hardcoded port collides the moment you run two instances. Step 3 is the bug most people ship. NsdManager silently renames your service on collision — "devmon" becomes "devmon (2)". If you cache the name you requested instead of reading the callback, your unregister call later fails silently. We read it back. Step 5 — one thread per peer, and it reconnects. During testing a service record went stale and the port changed underneath us; update_service tore the reporter down and re-pointed it automatically. That path is exercised, not theoretical. Point at the right-hand card: eight interfaces on this laptop, and only one is the real route. Naive code grabs the first NIC and reports a dead 169.254 link-local address. We resolve the actual route with a UDP connect — no packet sent, just the routing decision.

Why a certificate bundle?

The failure

$ pip install zeroconf psutil
SSLError(SSLCertVerificationError(
  "[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify
   failed: self-signed certificate in certificate chain"))

The cause

The corporate network intercepts TLS: it terminates the connection to PyPI, re-signs it with an internal root, and hands you that instead. Windows trusts that root. Python does not — pip 23 ships its own CA list (certifi) and ignores the OS store entirely.

Not a Python problem

Same root cause hits npm, gradle, git, curl — anything shipping a private trust store.

Three ways out

--trusted-host

Disables verification. Works, but you are now downloading and executing code over an unverified channel. Fine to bootstrap, wrong as a default.

Export the OS trust store

What this repo does: 267 Windows roots → PEM, pinned via pip.conf. Verification stays on; pip simply trusts what Windows already trusts.

Skip it — upgrade pip

pip ≥ 24.2 reads the Windows store natively (truststore). No bundle, no flags, nothing to regenerate.

py -m venv .venv
.venv\Scripts\python -m pip install --trusted-host pypi.org \
  --trusted-host files.pythonhosted.org --upgrade pip
.venv\Scripts\python -m pip install -r requirements.txt  # no flags
Tested on this machine: pip 23.2.1 fails · pip 26.2 succeeds with no flags
Two questions to answer here: why does this exist, and can we skip it. Click 1 — the error. Anyone setting this up on a corporate laptop sees exactly this, and it looks like a broken package index. It isn't. Click 2 — the cause, and this is the bit worth understanding. The network is doing a deliberate man-in-the-middle: it terminates your TLS session to PyPI, inspects the traffic, then re-signs it with an internal corporate root before handing it over. That's standard practice for traffic inspection. Windows was configured to trust that root, so browsers are fine. But pip 23 ships its own bundled CA list called certifi and does not consult the Windows store at all — so from pip's point of view it is being attacked, and it correctly refuses. Click 3 — generalise it. This is not Python-specific. npm, gradle, git and curl all ship or reference their own trust stores, and all break the same way in this environment. Click 4 — the tempting wrong answer. --trusted-host makes the error go away by turning verification off. You are then fetching executable code with no authentication whatsoever. It's acceptable for one bootstrap step, not as a standing configuration. Click 5 — what the repo actually does. Export the Windows roots to a PEM, point pip at it. Verification remains fully on; we've just told pip to trust the same authorities the OS trusts. Cost: a 450 KB file that is machine-specific and needs regenerating if IT rotates the root. Click 6 — and here is the direct answer to "can we skip the setup". Yes. Newer pip has a truststore feature that reads the Windows certificate store natively, which is exactly what we hand-rolled. I tested both on this machine: the pip 23.2.1 that ships with Python 3.11 fails, and after upgrading to pip 26.2 a plain install with no flags succeeds. The one wrinkle — you need a working pip to upgrade pip, and the bundled one can't reach PyPI. So bootstrap that single upgrade with --trusted-host, then everything after it verifies properly. One unverified step to fetch pip itself, instead of every install forever. If asked which to use: new setups take the pip upgrade. The bundle stays in the repo because it also fixes Gradle and works on machines pinned to old pip.

Other environment friction

Three more things that blocked a fresh setup — all handled inside the scripts, so tools/test-emulator.sh needs no setup at all.

Cert: provider missing

PowerShell's certificate drive is absent on this install, so export-ca-bundle.ps1 reads the store through .NET X509Store instead.

Python not on PATH

3.11 is installed but only the py launcher is exposed, so scripts resolve the interpreter explicitly rather than assuming python resolves.

Git Bash path mangling

Why this earns a slide

None of these are visible in the source, and each costs a fresh clone real time to rediscover. So the fixes live in the scripts — not in a setup document nobody reads.

Move briskly. This is reference material, not argument — skip it entirely if the audience isn't the people who will run the code. The through-line: all three are environment quirks invisible in the source, and each one costs twenty minutes to rediscover. Git Bash is the worst offender. It helpfully rewrites anything resembling a Unix path into a Windows path, which silently breaks adb commands that reference /sdcard. Setting MSYS_NO_PATHCONV=1 disables that — but then it also stops converting the APK path, which adb needs in Windows form. So the script disables conversion globally and explicitly converts the one path that needs it. The payoff is the bottom card. The fixes are inside the scripts, so someone cloning this repo runs one command and it works.

The emulator cannot discover

The AVD sits behind QEMU's user-mode NAT. Multicast does not cross that virtual router — so mDNS cannot reach your LAN, and nothing on the LAN reaches the emulator. 

$ adb shell ip -o addr show
1:  lo     inet 127.0.0.1/8
15: eth0   inet 10.0.2.15/24   ← QEMU NAT (reported LTE)
16: wlan0  inet 10.0.2.16/24   ← virtual AP, also internal

A correction worth making

First diagnosis was "no WiFi interface." Wrong — wlan0 and hwsim0 exist. It boots down, with the default route on LTE-flavoured eth0.

Bring the virtual WiFi up

$ adb shell cmd wifi \
    connect-network AndroidWifi open

Registration then succeeds: MdnsAdvertiser.wlan0: Probing finished. A queued service completed within a second of wlan0 appearing — after 11 minutes parked.

Still not cross-machine

10.0.2.16 is inside the NAT. The AndroidWifi AP is emulator-internal; Windows --list finds nothing. A physical device is required for real discovery.

This is the most important slide in the deck. Do not rush it. The headline: you cannot test mDNS discovery on an emulator. Not a bug in our code, not a firewall setting — the emulator's network stack does not forward multicast. Own the correction openly. The first diagnosis was that the AVD has no WiFi interface. That was wrong, and checking /sys/class/net showed wlan0 and hwsim0 both present. What's actually true: wlan0 boots DOWN, and the default route is eth0, which dumpsys reports as a CELLULAR transport. NsdManager needs a multicast-capable network up, and LTE-flavoured eth0 doesn't qualify. Then the useful discovery. One command brings the virtual AP up, and registration immediately succeeds. The evidence is the timeline: a service registered at 10:30 sat parked for eleven minutes and finished probing within one second of wlan0 appearing. Parked, not failed. So the emulator is more useful than first stated — it can exercise the real NsdManager success path and the Advertising UI state. What it still cannot do is talk to another machine. If asked "so is the emulator useless?" — no. Two modes, next slide.

Two emulator modes, one gap

MODE A

adb forward + --connect

Covers: TCP server, wire format, peers UI, reconnect, JSON parsing.

Misses: all of NsdManager.

MODE B

cmd wifi connect-network

Covers: registration, probing, collision rename, the Advertising UI state.

Misses: cross-machine discovery.

PHYSICAL DEVICE

The only way to test discovery for real.

Watch for AP client isolation on guest/corporate WiFi, and routers splitting 2.4 / 5 GHz onto separate subnets.

A footgun worth naming

The app binds port 0, so the port changes on every restart. A stale adb forward still accepts on 9999 and then silently fails to reach the dead device port — the client prints [+] connected and nothing ever arrives. tools/forward.sh re-reads the live port from logcat.

Three columns, then the footgun. Modes A and B are complementary, and neither replaces hardware. Mode A tunnels over ADB so the NAT is irrelevant — it tests everything above the transport. Mode B brings the virtual AP up and tests the NsdManager path. Together they cover most of the code; the discovery handshake between two machines is the residual gap. The footgun cost real debugging time in this session, so it earns its space. Symptom: client says connected, phone never updates, no error anywhere. The cause is a stale forward pointing at a port from a previous app run. adb forward happily accepts your connection and then can't reach the dead port. Fix is tools/forward.sh, which reads the live port out of logcat instead of trusting a remembered number. It was tested against exactly that failure — force-stop the app, relaunch, re-run, and it picks up the new port. Rule of thumb for the audience: after any app restart, re-run forward.sh.
