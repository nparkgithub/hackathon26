Use this prompt in Claude Code from the root directory of APK B:

You are working in an Android project that currently builds APK B.

Objective

Use APK B as the base application and integrate only the necessary functionality from APK A.

The final application must:

1. Keep APK B’s existing UI, networking, server communication, configuration, and sending behavior.
2. Add APK A’s image acquisition and image-labeling functionality.
3. Remove the current intermediate file-based workflow:
    * APK A saves a JPG image.
    * APK A saves a TXT label file.
    * APK B reads the JPG and TXT files.
    * APK B sends them.
4. Replace it with a direct in-memory pipeline:

Image acquisition
    → image processing or labeling
    → JPEG ByteArray plus label text
    → APK B sender
    → remote server

Do not rewrite the entire application. Make incremental, reviewable changes and preserve the existing working behavior until the new pipeline is verified.

Project locations

APK B, the base project:

<APK_B_PROJECT_PATH>

APK A, the source of image and labeling functionality:

<APK_A_PROJECT_PATH>

Work primarily inside APK B. Treat APK A as read-only unless absolutely necessary.

First step: inspect both projects

Before modifying code:

1. Analyze both Gradle project structures.
2. Identify:
    * Application modules
    * Android library modules
    * Package names and namespaces
    * Kotlin and Java source locations
    * Camera or image-input code in APK A
    * Image preprocessing code
    * Model loading and inference code
    * Label generation code
    * JPG-writing code
    * TXT-writing code
    * File-reading and directory-monitoring code in APK B
    * Network sender and upload request code in APK B
    * JNI, C++, CMake, native libraries, assets, model files, and ABI settings
    * Required Android permissions
    * ProGuard or R8 rules
    * Manifest entries
    * BuildConfig values and server configuration
3. Produce a concise integration plan before making major changes.
4. Clearly list which APK A classes should be reused, adapted, or excluded.
5. Do not copy APK A’s Activity, Fragment, Compose screens, navigation, theme, or complete application structure unless a specific dependency makes it necessary.

Target architecture

Prefer this project structure inside APK B:

APK_B_PROJECT/
├── app/
│   ├── existing APK B UI
│   ├── existing APK B network sender
│   ├── pipeline coordinator
│   └── final APK
│
├── image-processing/
│   ├── APK A image acquisition code
│   ├── image preprocessing
│   ├── model loading
│   ├── inference and labeling
│   └── JPEG conversion
│
└── core/
    ├── shared data models
    └── small interfaces

Create :image-processing and :core Android library modules only when they improve separation without introducing unnecessary complexity.

If APK A’s functionality is small and has no complex Android dependencies, placing it in a well-isolated package inside APK B is acceptable. Explain the choice before implementing it.

Shared data model

Create or adapt a shared result model similar to:

data class ProcessedImage(
    val jpegBytes: ByteArray,
    val labelText: String,
    val timestampMillis: Long,
    val width: Int,
    val height: Int,
    val confidence: Float? = null
)

Adjust the fields based on the actual server request and APK A output.

Do not pass file paths between the image-processing and network layers.

Image-processing API

Expose APK A’s useful functionality through a small API.

Use one of these patterns based on the existing implementation:

interface ImageProcessor {
    suspend fun process(bitmap: Bitmap): ProcessedImage
}

or:

interface ImageCaptureProcessor {
    suspend fun captureAndProcess(): ProcessedImage
}

Do not expose APK A’s internal model, camera, storage, or UI implementation details to APK B’s sender.

Modify APK B’s sender

APK B currently reads an image file and a text file before sending.

Refactor the sender so its primary API accepts memory data:

suspend fun send(result: ProcessedImage): Result<Unit>

or:

suspend fun send(
    jpegBytes: ByteArray,
    labelText: String
): Result<Unit>

Reuse APK B’s existing:

* Endpoint
* Authentication
* HTTP or socket implementation
* Metadata
* Error handling
* Request format
* Server response processing

Avoid changing the server protocol unless required.

If the server expects multipart file parts, create those parts directly from ByteArray and label text without writing temporary files.

Migration strategy

Implement the migration in safe phases.

Phase 1: Refactor without behavior changes

In APK A functionality, separate processing from file saving.

Transform code conceptually from:

val image = captureImage()
val label = createLabel(image)
saveJpeg(image, imageFile)
saveText(label, labelFile)

into:

val result = processImage()
legacyWriter.save(result)

The processing function should return ProcessedImage.

Phase 2: Add direct sender support

Add an in-memory sending method to APK B while keeping its existing file-based sender temporarily.

The existing file-based method may adapt files into ProcessedImage and delegate to the new sender.

Example:

suspend fun sendFiles(
    imageFile: File,
    labelFile: File
): Result<Unit> {
    val result = ProcessedImage(
        jpegBytes = imageFile.readBytes(),
        labelText = labelFile.readText(),
        timestampMillis = imageFile.lastModified(),
        width = 0,
        height = 0
    )
    return send(result)
}

Avoid duplicating the actual networking implementation.

Phase 3: Connect the direct pipeline

Create a coordinator or use-case class:

class CaptureProcessSendUseCase(
    private val processor: ImageProcessor,
    private val sender: ResultSender
) {
    suspend operator fun invoke(): Result<ProcessedImage> {
        return runCatching {
            val processed = processor.process()
            sender.send(processed).getOrThrow()
            processed
        }
    }
}

Adapt this design to the actual codebase.

Phase 4: Verify both paths

Temporarily support:

Legacy path:
process → save JPG/TXT → read files → send
New path:
process → ProcessedImage → send directly

Compare:

* Image byte size
* JPEG dimensions
* JPEG quality
* Label text
* Confidence values
* Request payload
* Filename or metadata sent to the server
* Server response
* Processing latency
* Upload latency
* Memory use

Phase 5: Remove obsolete file exchange

Only after the direct path builds and works, remove:

* JPG intermediate saving
* TXT intermediate saving
* Directory polling or file watching
* Filename matching between JPG and TXT
* Re-reading image bytes
* Re-reading label text
* Storage permissions that are no longer required
* Obsolete retry or cleanup logic tied only to the file exchange

Do not remove persistent storage if it is still needed for offline retry, audit history, or recovery.

Network failure behavior

Determine whether APK B currently relies on files as an upload retry queue.

If files provide retry capability, do not silently remove that reliability.

Implement one of these approaches:

1. Direct in-memory sending with a disk fallback only when sending fails.
2. A WorkManager-based persistent upload queue.
3. Preserve the existing retry storage behind a clean queue interface.

The normal successful path should not write and reread files.

Document which approach was selected.

Camera and image lifecycle

When moving APK A’s camera or CameraX code:

* Preserve lifecycle binding.
* Preserve camera permissions.
* Close every ImageProxy.
* Avoid retaining Activity or Fragment references in long-lived objects.
* Do not perform inference or JPEG compression on the main thread.
* Use lifecycle-aware coroutine scopes.
* Prevent unlimited processing when frames arrive faster than inference or sending.

For continuous frames, use a bounded queue or drop-oldest policy rather than creating unlimited coroutines.

Bitmap and memory handling

Avoid unnecessary conversion chains such as:

Bitmap
→ JPG file
→ read JPG bytes
→ decode Bitmap
→ encode JPG again

Prefer:

Camera image
→ model input
→ one JPEG encoding
→ network body

Be careful with large Bitmap and ByteArray allocations.

Do not call Bitmap.recycle() when ownership is unclear or when another component may still use the bitmap.

Native and model dependencies

If APK A uses JNI, C++, TensorFlow Lite, ONNX Runtime, Qualcomm libraries, or another inference runtime:

1. Move all required source and binary dependencies.
2. Preserve:
    * CMakeLists.txt
    * externalNativeBuild
    * cppFlags
    * abiFilters
    * .so libraries
    * model assets
    * delegate initialization
    * ProGuard/R8 rules
3. Verify native library loading after any package or module changes.
4. Avoid changing JNI method signatures unless necessary.
5. Confirm that model asset paths still work from the new module.

Naming

Keep APK B’s current applicationId during integration.

Do not change the application ID, package identity, signing setup, database identity, provider authorities, or OAuth configuration unless explicitly required.

Testing requirements

Add focused tests where practical.

At minimum, test:

1. Processing a known sample image produces non-empty JPEG bytes.
2. Processing produces non-empty label text.
3. The sender receives the same bytes and label generated by the processor.
4. The multipart or request body contains the expected image and text fields.
5. Failure from the server returns a useful error.
6. Repeated processing does not create an unbounded queue.
7. The app builds for all currently supported ABIs and build variants.

Use a fake sender to test the pipeline without a real server:

class FakeResultSender : ResultSender {
    var lastResult: ProcessedImage? = null
    override suspend fun send(
        result: ProcessedImage
    ): Result<Unit> {
        lastResult = result
        return Result.success(Unit)
    }
}

If there are no existing tests, add only a small, maintainable test set rather than introducing a large new test framework.

Coding quality

Follow the existing project’s coding conventions.

Prefer:

* Small classes
* Constructor dependency injection
* Explicit ownership of image data
* Structured concurrency
* Dispatchers.IO for blocking network or file operations
* Dispatchers.Default for CPU-heavy image processing
* Clear error messages
* Minimal public API surface
* No hidden global state

Avoid:

* Static global Activity or Context references
* Direct dependency from the image-processing module back to the app module
* Broad singleton objects that mix camera, inference, storage, and networking
* Duplicate networking code
* Blocking work on the main thread
* Catching and ignoring exceptions
* Temporary files in the normal successful path
